## Research → dev

Non-trivial work is research-first: findings go to `docs/research/` **before** implementation,
never left in chat history.

**Doc flow:** `docs/research/` → `docs/adr/` → `docs/issues/` → source +
`docs/d2r-mobile-architecture.md`. An ADR cites the research that justified it.

**Naming:** `docs/research/YYYY-MM-DD-<slug>.md`; a directory `YYYY-MM-DD-<slug>/` with a numbered
`NN-<slug>.md` series is reserved for a huge epic.

**Mandatory for:** a new subsystem (PC input, window modes, gamepad) · any HarmonyOS API or
platform behaviour we have not used before · any choice that will become an ADR · patch-locally
vs. send-upstream forks. **Not for:** bugfixes and work an existing doc already covers.

**Machine provenance is mandatory.** Every finding that depends on a device says which device,
firmware, API level and build it was observed on (`oh device info` fields
`const.product.model` / `const.product.software.version` / `const.ohos.apiversion`). What was
not verified on a device is a stated limitation. Upstream's numbers stay tagged as upstream's
(see `CONTEXT.md` §4).

## Work units — task · epic · huge epic

| Unit | Shape | Tracked by | Exit |
|---|---|---|---|
| **Task** | One issue, a few commits | `docs/issues/NNN` | The issue's `## Exit` |
| **Epic** | One goal, several issues, one research doc | Umbrella issue + `docs/research/<date>-<slug>.md` | The umbrella issue's `## Exit` |
| **Huge epic** | Several epics aimed at one very big goal (a port, a new device class) | Umbrella issue + `docs/research/<date>-<slug>/` with an epic SOT | Human end-to-end evaluation on real devices, then a version bump |

The test for "huge" is that no existing gate can verify the goal, so the epic needs its own metrics.

### Huge epic protocol

Steps are ordered; a later step never starts before the earlier one is recorded.

1. **Charter.** Umbrella issue + `docs/research/YYYY-MM-DD-<slug>/` holding `README.md` (index,
   doc status, known disagreements) and `00-epic-sot.md` (single source of truth: read before,
   update after). The directory is never renamed.
2. **Research wave.** Research docs land in the directory as the next `NN-<slug>.md`;
   the orchestrator adjudicates disagreements in the SOT.
3. **Metrics before code.** The SOT's `## Metrics` table (id, what, exact command, **baseline
   measured now**, target, judge) is agreed with the human before wave 1, then frozen; a change
   is a dated SOT decision with the reason.
4. **Dev waves.** Task spec → sub-agents implement → the orchestrator re-runs the gate and scores
   **every** wave metric itself → dated progress row with numbers and commit hashes → commit.
   A missed target is fixed in the same wave or becomes a dated SOT decision.
5. **Human e2e exit.** The human runs the exit metrics on real devices and records the verdict in
   the SOT. Findings become issues; plan for more than one round.
6. **Delivery.** Version bump, `CHANGELOG.md` entry linking the SOT, tag, an ADR per recorded
   decision, SOT closed with date and version, umbrella issue `closed-verified`, ledger + daily.

## Session orchestration

The main session orchestrates; sub-agents implement. Sub-agents inherit the session's model;
a cheaper tier only for mechanical batches, never for research, adjudication or scoring.

- **Main session owns:** requirement shaping, decisions, task specs, verification (**re-run the
  gate yourself before committing, never on a sub-agent's word**), commits and pushes, ledger /
  SOT records, anything touching devices, signing material or the user's game files.
- **Sub-agents own:** research sweeps and implementation batches against the working tree.
- **Stays in the main session:** one-liners, doc touch-ups, read-only spot checks, and **all
  on-device runs** (one device, one driver at a time).

### Concurrency cap — at most **3** sub-agents in flight

**Hard rule**, per session, counted over all live sub-agents. Changing it needs an ADR. Why:
(1) the main session goes blind while they run; (2) parallel agents on overlapping subjects
produce authoritative-looking contradictions; (3) the machine is shared (6 cores / ~9 GB on
oh-vm) and every agent is a full tool loop; (4) writable agents in one tree collide.

How to work under it: cut by interface, not file count · read-only agents may run wider than
writable ones, writable ones never overlap · one agent with two related outputs beats two agents ·
`dependency → dependent` is a second wave, not a fourth agent · below ~10 minutes of work,
do it here. **Enforced by record:** state each wave's batch and size in the SOT wave row; if the
cap is exceeded, say why in the same row.

**Task spec** for a sub-agent: (1) required reading — this file, the SOT, relevant ADRs,
`CONTRIBUTING.md` for anything under `dm/`; (2) environment traps — copy the *Environment traps*
list below verbatim, sub-agents inherit nothing; (3) hard boundaries — no commits, no device
runs, no edits to upstream files unless the spec says so; (4) return format — file list, gate
output, spec deviations with reasons; (5) an interrupted agent is resumed from its transcript
("check `git status`, reconcile, continue"), never restarted; (6) new facts go to the running
agent as a follow-up message.

## What d2r-mobile is

`d2r-mobile` (this fork) is **a downstream fork of jhaizhou-ops/d2r-mobile whose job is to make
the HarmonyOS port run flawlessly on HarmonyOS PC (2in1) and HarmonyOS phones — install, import,
play, save, at a stable 60 fps, with touch, keyboard/mouse and gamepad input** — and nothing more.

It is **not** the home of the iOS / macOS / tvOS / Android ports or of the shared engine roadmap
(those live upstream; shared-code fixes go back there as PRs), and it **never** ships game content
(players bring their own Switch files). Detail: [positioning](docs/d2r-mobile-positioning.md).

Target devices (the only ones a claim may be made about): **HUAWEI MateBook Pro S** (`MOR-M1`,
devicetype `2in1`, API 26, the host this VM runs on; hdc `172.16.105.1:<port>`) and **HUAWEI
Mate X5** (foldable phone; API level unverified — the HAP requires API 26). Upstream's Mate 90
Pro Max / Pura X results are upstream's, not ours.

### Environment traps (copy into every sub-agent spec)

- **Build HarmonyOS packages with `oh build` / `oh pkg` / `oh app`, never raw `hvigorw` / `hdc`**
  (skills `vm-openeuler`, `oh-build`, `host-hmos`). This VM is aarch64 openEuler with the native
  linux-arm64 Command Line Tools; upstream's docs assume DevEco Studio on Windows.
- **Bare `diff` is broken here** (PATH-shadowed x86_64 binary → `Exec format error`); use
  `/usr/bin/diff`, `cmp` or Python. A sub-agent that reads `Exec format error` as "files differ"
  produces a false report.
- **`df` in this guest lies.** Read the host water level via the `disk-guard` skill before any
  large job; an import pack + game data is ~17 GB `(upstream-reported)`.
- **The host's home is `/mnt/linux_share/storage/Users/currentUser/`**; `~` here is the guest.
  Anything the user must see on the PC goes there by absolute path (skill `to-doc`).
- **Generators write into the tree.** `dm/harmony/tools/gen_strings.py` rewrites
  `entry/src/main/ets/generated/UiText.ts` even when called with `--help`; on 2026-10-26 that file
  was stale against `dm/i18n/ui_text.tsv` ([issue 008](docs/issues/008-harmony-uitext-drift.md)).
  Don't run generators casually; if one dirties an upstream file, `git checkout` it.

### Resources — one heavy job per machine

1. Before a heavy run (HAP build, `setup.sh`, shader translation, `cargo`): check
   `pgrep -x cargo || pgrep -x rustc || pgrep -x box64 || pgrep -x java` — hvigor runs under
   `node`/`java`. Prefer `-x` over `-f` (the `-f` form matches the waiting shell itself).
2. One in-flight heavy job per machine; sub-agents queue on rule 1.
3. **Never `git stash` a shared tree.** Use `git worktree` to isolate.
4. Long runs go to the background with a log in the scratchpad.
5. Report the cost: wall-clock, peak RSS, exact command, in the issue or SOT.

### Disk hygiene

Game files, `$DM_ROOT` (default `~/dm-work`), import packs and hvigor caches are tens of GB, all
**outside git** and regenerable except the user's game files. On this thin-provisioned host a
full disk is data corruption: check the real water level first, purge reproducible caches at
wrap-up, and remember a purge breaks runs that expect prebuilt artifacts.

## Design principles — at-hand summary

Full text in [`docs/d2r-mobile-design-philosophy.md`](docs/d2r-mobile-design-philosophy.md).

1. **Upstream-first.** A fix in shared code (`dm/host`, `dm/gfx`, `dm/android`, `dm/tools`) is
   written as an upstream PR; local divergence lives only in `dm/harmony/` or behind `__OHOS__`.
2. **Measured on our device, or not claimed.** Every "works" / fps number names device, firmware,
   API, build and command.
3. **One HAP for phone and PC.** Device differences are detected at run time (device type, window
   mode, input source), never by a second package.
4. **PC is not a big phone.** Keyboard, mouse, gamepad and resizable windows are first-class on
   PC; the touch overlay is opt-in there, not the only control scheme.
5. **Saves are sacred.** No workaround may uninstall the app, change the signing identity, or
   touch the save directory; upgrades are signed over the top.

| Signing identity (bundle name + cert) | Upgrades install over the top only with the same identity; saves live in the app sandbox | Never change it on a device with saves |
| `dm/PRODUCT` codename (`3.3.94012-r44` today) | Ties pack, shell and tools to one source version | Bump only via upstream |

## Hard rules

- **No game content in git, ever** — game program, art, text, shaders, saves, generated packs,
  or any HAP that embeds them (`*.hap` is already gitignored). Upstream CONTRIBUTING rule 1.
- **No signing material in git.** Certificates, profiles (`*.cer`, `*.p7b`), keystores and
  passwords live under `/private/` (gitignored) or outside the repo; `*.cer` / `*.p7b` are **not**
  covered by `.gitignore` — check `git status` before every commit.
- **Upstream files are not edited on `main`** (ADR-0001). Changes to them go on a branch cut from
  upstream for a PR, following upstream's CONTRIBUTING (bilingual comments, string table, checks
  stated). Exception: none yet; adding one needs an ADR.
- **`dm/third_party/` is vendored upstream code** — never edited, never linted.
- **Never uninstall an app with saves** to get past an install error; fix the signature instead.
- Device actions (install, launch, UI drive, logs) go through `oh`, one driver per device at a time.

3. **One sub-agent per sibling repo**, reading that repo's `CLAUDE.md` and issue conventions

## Commit style

Two kinds of commit, never mixed:

- **Ours, on `main`:** conventional commits with the issue id —
  `feat(harmony): … (#004)`, `docs(epic): …`; scope = `harmony` / `docs` / `epic` / `tools`.
- **Upstream-bound, on a PR branch cut from upstream:** upstream's style — one plain English
  sentence describing the player-visible effect (see `git log`), bilingual comments, checks run
  listed in the PR body per upstream's PR template.

Attribution trailers follow the session's harness instructions.
